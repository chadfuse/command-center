How I Built an Automated AI-Powered Content Distribution System

This post walks through the entire build of an automated content distribution app that generates blog posts with AI and publishes them to WordPress, LinkedIn, Facebook, and Instagram on a schedule. It runs entirely on free tiers and is deployed on Cloudflare Workers.

What the project does

The app is called Auto-Poster. It is a Cloudflare Worker that does the following automatically:

  • Generates 1000+ word SEO blog posts with a featured image.
  • Publishes the full blog post to WordPress twice per week.
  • Publishes adapted social posts to LinkedIn, Facebook, and Instagram twice per day.
  • Picks unique topics from RSS feeds and a static list, storing used topics in KV to avoid duplicates.
  • Sends email notifications for every successful or failed run via Resend.
  • Supports real stock images from Unsplash with AI fallbacks from Pollinations and Cloudflare Workers AI.

Tech stack

  • Cloudflare Workers for the runtime and cron scheduling.
  • Cloudflare KV for topic deduplication and queue state.
  • Groq OpenAI-compatible API for text generation.
  • Cloudflare Workers AI for image fallback.
  • WordPress REST API for the blog.
  • LinkedIn, Facebook, and Instagram APIs for social posts.
  • Resend for email notifications.

Step 1: Create the Cloudflare Worker project

I created a new directory and used Wrangler to scaffold a Cloudflare Worker project. The main file is src/index.js, and the config is in wrangler.toml.

npx create-cloudflare command-center
cd command-center
npm install

The Worker exposes two handlers:

  • fetch — for manual posts and helper endpoints.
  • scheduled — for cron-triggered posts.

Step 2: Generate text with an AI model

I use the Groq API through an OpenAI-compatible endpoint. The prompt asks the model to return the post in a strict format with title, slug, focus keyword, meta description, excerpt, tags, and a long HTML body.

The model sometimes produced shorter content, so I added an expansion step. After the first generation, the Worker counts words. If the body is under 800 words, it sends the draft back to the model with an instruction to expand it to at least 1000 words.

Step 3: Generate and upload the featured image

The image generation works in three layers:

  1. Unsplash — if an UNSPLASH_ACCESS_KEY is set, the Worker searches Unsplash for a real stock photo related to the topic and uploads it to WordPress.
  2. Pollinations — if Unsplash fails or is not configured, it calls the free Pollinations AI image API.
  3. Cloudflare Workers AI — as a final fallback, it uses @cf/black-forest-labs/flux-1-schnell.

The image is always uploaded to WordPress so it has a public URL. That URL is required by Instagram, which cannot pull images from a local source.

Step 4: Publish to WordPress

The Worker creates a WordPress post through the REST API and sets the following fields:

  • Title, slug, content, status, and excerpt.
  • Featured media.
  • Yoast SEO meta: _yoast_wpseo_title, _yoast_wpseo_metadesc, and _yoast_wpseo_focuskw.
  • RankMath SEO meta: rank_math_title, rank_math_description, and rank_math_focus_keyword.

The scheduled cron for WordPress uses status: publish. Manual test calls can override this to draft by setting "wp": { "status": "draft" }.

Step 5: Post to LinkedIn

LinkedIn posting uses the /v2/ugcPosts endpoint. The text includes the title, a short body preview, and a link to the WordPress post. To avoid the boring text-only look, I added an image upload flow:

  1. The Worker downloads the featured image from WordPress.
  2. It registers the image asset with LinkedIn.
  3. It uploads the binary to the pre-signed upload URL.
  4. It creates the LinkedIn post with shareMediaCategory: "IMAGE".

Step 6: Post to Facebook

Facebook posts are published to a Facebook Page using a Page token. The message format is different from the blog: it uses the title, the excerpt, and a social CTA instead of the full blog body, so it does not look like a copy-paste of the article.

The link shared on Facebook falls back to the WordPress homepage when a new blog post is not available on that run.

Step 7: Post to Instagram

Instagram requires a Business or Creator account and a Facebook token with instagram_basic and instagram_content_publish permissions. The Worker does the following:

  1. Creates a media container with the public WordPress image URL and a short caption.
  2. Waits 10 seconds for the media to be ready.
  3. Publishes the media container.
  4. Fetches the final permalink and shortcode so the response contains the live Instagram URL.

Step 8: Avoid duplicate topics with RSS feeds and KV

To keep every post unique, the Worker fetches four RSS feeds and combines them with a static CRON_TOPICS list. It then checks a Cloudflare KV namespace called POSTED_TOPICS for the slugified topic. If a topic was already used, it skips it. After a successful post, it stores the topic in KV.

This means the schedule can keep running without repeating the same content.

Step 9: Add cron scheduling

The cron triggers in wrangler.toml are:

[triggers]
crons = ["0 8 * * 1,4", "0 10 * * *", "0 18 * * *"]
  • Monday and Thursday at 08:00 UTC — WordPress blog post.
  • Every day at 10:00 and 18:00 UTC — LinkedIn, Facebook, and Instagram.

Step 10: Long-lived Facebook and Instagram tokens

Tokens from the Graph API Explorer expire in about an hour. To avoid resetting them constantly, I added a /refresh-facebook-token helper endpoint. The user sends their Facebook App ID, App Secret, short-lived User token, and Page ID, and the Worker exchanges it for a long-lived Page token.

This same token is used for both Facebook and Instagram, so you only need to refresh one credential.

Step 11: Email notifications with Resend

I integrated Resend so the Worker emails a summary after every run. The NOTIFICATION_EMAIL and FROM_EMAIL are configured in wrangler.toml, and the RESEND_API_KEY is stored as a secret.

To send to any third-party email address, the FROM_EMAIL domain must be verified in Resend by adding the DNS records it provides.

Step 12: Deploy and push to GitHub

The project is deployed with:

npx wrangler deploy

And pushed to a private GitHub repo at chadfuse/command-center using gh.

How to use it manually

You can trigger a single post with a curl request:

curl -X POST https://auto-poster.chadfuse.workers.dev \
  -H 'content-type: application/json' \
  -d '{
    "topic": "How to use AI to speed up WordPress development",
    "niche": "AI and WordPress development",
    "platforms": ["wordpress", "linkedin", "facebook", "instagram"],
    "wp": { "status": "publish" }
  }'

What went wrong and how I fixed it

  • LinkedIn image posts failed — LinkedIn ARTICLE media requires a registered asset. I switched to uploading the image first as an IMAGE asset.
  • Instagram caption too long — I switched the caption to use the excerpt instead of a large body slice.
  • Facebook token expired every hour — I built the /refresh-facebook-token endpoint to exchange short-lived tokens for long-lived Page tokens.
  • Resend emails did not arrive — The FROM_EMAIL domain had not been verified. After verifying chadsia.com in Resend, it worked.
  • AI-generated images looked messy — I added Unsplash as the primary image source and kept AI as a fallback.

Limitations, pain points, and free-tier constraints

Built only with free services

Every service used in this project is on a free tier. The text model is the free allam-2-7b from Groq. Images come from Unsplash and Pollinations first, with Cloudflare Workers AI as a last resort. Email uses Resend's free tier. The runtime is Cloudflare Workers' free tier.

Because of that, there are hard limits. The allam-2-7b model has a 6000 token-per-minute limit and sometimes produces short or dated output. It cannot browse the live web, so the "current" content in posts is based on its training data, not live research. The free Resend plan requires domain verification before sending to third-party addresses. Unsplash is limited to 50 requests per hour.

Built with Devin SWE-1.7 (free LLM)

This entire project was built from start to finish using the free Devin SWE-1.7 coding model. There was no paid IDE, no premium agent, and no commercial coding assistant. Every file, endpoint, and integration was generated and debugged through the free plan.

That also meant slower iteration, more back-and-forth, and careful rate management. The model could not pull live data, so we had to rely on RSS feeds and static topic lists instead of real-time research.

Pain points we hit

  • Short AI outputs — allam-2-7b did not always reach 1000 words. I added a second expansion call, but the free model still has a ceiling.
  • Outdated AI knowledge — The model cannot know what happened this week. RSS feeds fix some of this, but not for topics with no news.
  • Image quality — Free AI image generators often produce abstract or messy images. Unsplash helped, but stock photos do not always match the exact topic.
  • Token expiry — Facebook and Instagram tokens from Graph API Explorer expire in about an hour. I had to build a custom token exchange endpoint to get long-lived tokens.
  • Permission confusion — The Facebook Page did not appear in me/accounts until business_management was added to the token permissions.
  • Resend domain verification — Emails did not send until chadsia.com was verified with full DNS records.
  • Instagram publishing delays — The media container is not immediately publishable. I had to add a 10-second wait before calling media_publish.
  • Rate limits — Two AI calls per post for text plus image generation plus social posts meant we had to keep token budgets tight and wait between tests.

Final notes

The system is now live, scheduled, and fully automated. It generates long-form content, publishes to the blog, and distributes social posts daily using only free tiers of Groq, Cloudflare, Resend, Unsplash, and Pollinations. The entire build was done with the free Devin SWE-1.7 coding model.

It is not perfect. The AI can be short, the images are sometimes generic, and the social platforms have tight token and permission rules. But for a fully free, automated content distribution pipeline, it is stable and working.

The repo is private at github.com/chadfuse/command-center, and the README includes full setup instructions.
